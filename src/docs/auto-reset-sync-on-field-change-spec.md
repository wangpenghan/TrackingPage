# 客运模板关键字段变更自动标记未同步设计方案

**版本：** v1.1
**日期：** 2026-05-08
**适用模块：** 客运模板 / 编辑抽屉 / 状态自动管理

---

## 1. 背景与目标

### 1.1 问题

当前用户编辑已同步的模板并保存后，`synced` 状态不会变化，导致：
- 目标系统（基本计划）持有的是**旧数据**
- 页面显示「已同步」，但实际数据已不一致
- 用户若不手动回退再同步，目标系统将长期持有过期数据

### 1.2 目标

对影响实际运营的关键字段建立监听机制，一旦值发生变更，自动将模板的 `synced` 重置为 `false`，提醒用户重新同步，确保数据一致性。

---

## 2. 触发字段清单（关键字段）

以下字段变更将自动触发标记未同步，依据是这些字段直接影响旅客服务、现场作业或闸机系统：

### 2.1 客运列车关键字段

| 字段名 | 业务含义 | 影响方向 |
| :--- | :--- | :--- |
| `arrivalTime` | 到达时间 | 旅客候车、现场调度 |
| `departureTime` | 发车时间 | 旅客候车、现场调度 |
| `entryCheckOffset` | 进站开检偏移 | 检票口开放时间 |
| `entryStopOffset` | 进站停检偏移 | 检票口关闭时间 |
| `exitCheckOffset` | 出站开检偏移 | 出站闸机开放时间 |
| `exitStopOffset` | 出站停检偏移 | 出站闸机关闭时间 |
| `track` | 股道 | 车辆调度、站台引导 |
| `gates` | 检票口 | 检票口现场布置 |
| `exitGate` | 出站口 | 出站口现场导引 |

### 2.2 非客运列车关键字段

| 字段名 | 业务含义 | 影响方向 |
| :--- | :--- | :--- |
| `arrivalTime` | 到达时间 | 现场调度 |
| `departureTime` | 发车时间 | 现场调度 |
| `track` | 股道 | 车辆调度 |
| `parkingSpot` | 停车位置 | 作业区域 |
| `hasWater` | 上水作业 | 作业需求 |
| `hasSuction` | 吸污作业 | 作业需求 |

> **不触发自动标记的字段**（属于内部管理信息，变更不影响已推送数据）：
> `bureau`、`broadcastGroup`、`trainClass`、`capacity`、`operator`、`operateTime`、`landmarkColor`、`diagramNo`、`carriages` 等。

## 3. 触发逻辑

### 3.1 触发时机

**保存时触发**（而非实时触发）：用户点击「保存」按钮时，系统对比「当前表单值」与「原始已同步数据值」，若任一关键字段存在差异，则触发标记。

> **不采用实时触发的原因：**
> 用户编辑过程中可能会反复修改再改回，实时触发会造成频繁状态变动和不必要的提示干扰。保存是明确的「用户意图确认」节点。

### 3.2 触发条件

```
if (模板当前状态为 synced === true)
  AND (保存时任一关键字段的新值 ≠ 原始值)
then
  synced ← false
  记录触发原因（哪些字段变更）
```

若模板本身是「未同步」状态，关键字段变更后仍保持「未同步」，无需额外操作。

### 3.3 字段比对规则

| 字段类型 | 比对方式 |
| :--- | :--- |
| 字符串（时间、股道等） | 严格相等（`===`），空字符串与 `undefined` 视为等价 |
| 数字（偏移量） | 严格相等（`===`） |
| 布尔值（作业标记） | 严格相等（`===`） |
| 逗号分隔字符串（检票口） | 排序后再比较，避免顺序不同误判为变更 |

## 4. 用户提示交互

### 4.1 保存时提示（弹窗确认）

检测到关键字段变更时，在执行保存前弹出提示：

```
┌────────────────────────────────────────────────────────┐
│  ⚠️  关键字段已修改，将重置同步状态                    │
│                                                        │
│  以下字段的修改将导致模板被标记为「未同步」：          │
│                                                        │
│  · 股道：4 → 5                                         │
│  · 发车时间：09:10 → 09:25                             │
│  · 检票口：4A、5A → 4A、5A、4B                        │
│                                                        │
│  保存后需重新执行同步操作，目标系统数据才会更新。      │
│                                                        │
│            [取消修改]    [确认保存并重置同步]          │
└────────────────────────────────────────────────────────┘
```

- **取消修改**：关闭弹窗，返回编辑状态，数据不保存。
- **确认保存并重置同步**：保存数据，将 `synced` 置为 `false`，抽屉关闭后列表该条记录同步状态更新为「未同步」。

### 4.2 保存成功后的列表提示

保存完成后，该条模板在列表中：
- 同步状态标签从「已同步（绿色）」切换为「未同步（橙色）」
- Toast 提示：`G473 已保存，同步状态已重置，请重新同步`

### 4.3 无需弹窗的情况

若模板本身 `synced === false`，或修改的字段全部不在关键字段清单内，直接保存，不弹提示，Toast 显示：`G473 已保存`。

## 5. 数据结构扩展

在 `TemplateData` 中增加两个辅助字段，用于追踪触发原因（可选，建议实现）：

```ts
// 在 TemplateData 中新增
syncResetReason?: string[]   // 本次重置同步的触发字段列表，如 ['track', 'departureTime']
syncResetTime?: string       // 重置同步的时间戳
```

这两个字段用于：
- 在同步记录面板中显示「上次因修改哪些字段被重置」
- 辅助用户理解为何处于未同步状态

## 6. 关键字段常量定义（实现参考）

```ts
// 触发自动重置同步状态的关键字段 - 客运列车
export const PASSENGER_SYNC_SENSITIVE_FIELDS: (keyof TemplateData)[] = [
  'arrivalTime',
  'departureTime',
  'entryCheckOffset',
  'entryStopOffset',
  'exitCheckOffset',
  'exitStopOffset',
  'track',
  'gates',
  'exitGate',
]

// 触发自动重置同步状态的关键字段 - 非客运列车
export const NON_PASSENGER_SYNC_SENSITIVE_FIELDS: (keyof TemplateData)[] = [
  'arrivalTime',
  'departureTime',
  'track',
  'parkingSpot',
  'hasWater',
  'hasSuction',
]

// 检测是否有关键字段变更
export function detectSyncSensitiveChanges(
  original: TemplateData,
  updated: TemplateData,
  isPassengerTrain: boolean
): (keyof TemplateData)[] {
  const fields = isPassengerTrain
    ? PASSENGER_SYNC_SENSITIVE_FIELDS
    : NON_PASSENGER_SYNC_SENSITIVE_FIELDS

  return fields.filter((field) => {
    const oldVal = original[field]
    const newVal = updated[field]

    // 逗号分隔字符串特殊处理（如 gates）
    if (typeof oldVal === 'string' && typeof newVal === 'string' && field === 'gates') {
      const normalize = (v: string) => v.split(',').filter(Boolean).sort().join(',')
      return normalize(oldVal) !== normalize(newVal)
    }

    // 空值归一化
    const normalize = (v: any) => (v === undefined || v === null || v === '') ? '' : v
    return normalize(oldVal) !== normalize(newVal)
  })
}
```

## 8. 与已有流程的关系

| 流程 | 与本方案的关系 |
| :--- | :--- |
| **确认流程**（confirmed） | 关键字段变更**不重置** `confirmed`，已确认的数据仍保持确认状态，只需重新同步 |
| **手动回退同步**（v1.1方案） | 手动回退是用户主动操作；本方案是系统自动感知，两者互补 |
| **批量同步**（v1.0方案） | 关键字段变更后，该车次会重新进入「未同步」分组，下次批量同步时自动纳入 |
| **同步记录查询** | `syncResetReason` 字段可在同步记录面板中展示「上次因何重置」，提升可追溯性 |

## 9. 边界情况处理

| 场景 | 处理方式 |
| :--- | :--- |
| 用户修改关键字段后改回原值再保存 | 比对后无差异，不触发重置，正常保存 |
| 同时修改多个关键字段 | 弹窗列出所有变更字段，一次提示，统一处理 |
| 模板处于「未同步」状态时修改关键字段 | 不触发弹窗，直接保存（本身已是未同步） |
| 模板处于「数据无效」状态时修改关键字段 | 不触发重置同步（无效数据无法被同步，无意义） |
| 批量编辑场景（未来功能）| 每条单独检测，有变更的单独重置，批量保存后统一 Toast 汇总提示 |
| 列车类型切换（客运→非客运）| 保留必要字段，清除客运专用字段 |
| 列车类型切换（非客运→客运）| 初始化客运专用字段为默认值 |
